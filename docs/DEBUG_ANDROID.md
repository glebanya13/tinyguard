# Диагностика на Android-телефоне

Если игра зависает, лагает или вылетает, а воспроизвести на компьютере не получается,
нужны данные с телефона. Ниже: что снять кабелем (`adb`), что показать прямо в игре без кабеля
и как это читать. Пакет игры: `com.bimbleguard.app`.

## 1. Подготовка

1. На телефоне: Настройки → О телефоне → 7 раз тапнуть «Номер сборки» → вернуться в
   Настройки → Для разработчиков → включить «Отладка по USB».
2. Подключить кабелем, разрешить отладку на телефоне.
3. На компьютере (Android platform-tools): `adb devices` должен показать устройство.

## 2. Лог вылета

Сразу после вылета (чем раньше, тем лучше: буфер короткий):

```sh
adb logcat -b crash -d > crash.txt
```

Полный лог с фильтром по игре и по тому, что убивает приложения:

```sh
adb logcat -c                       # очистить буфер, затем играть до вылета
adb logcat | grep -E 'godot|bimbleguard|AndroidRuntime|lowmemorykiller|ActivityManager|libc|DEBUG' > run.txt
```

Что искать в `run.txt`:

| Строка | Что значит |
|---|---|
| `lowmemorykiller`, `Killing ... (adj ...)`, `ActivityManager: Process com.bimbleguard.app ... has died`, `reason: ... memory` | Систему не хватило памяти, процесс убит. Смотрите `meminfo` ниже |
| `Fatal signal 11 (SIGSEGV)`, `backtrace:` с `libgodot_android.so` или `libGLES`/`libvulkan`/`libmali` | Падение в движке или драйвере GPU. Нужны модель телефона и GPU (`adb shell getprop ro.product.model`, `ro.hardware.egl`) |
| `AndroidRuntime: FATAL EXCEPTION` | Исключение в Java-части (редко) |
| `ANR in com.bimbleguard.app` | Главный поток Android не отвечал 5 с (экран загрузки, вызов, сеть) |
| `GL_OUT_OF_MEMORY`, `glError`, `ERROR:` от godot | Память GPU закончилась |
| `Skipped N frames!`, `Choreographer` | Игра не успевает рисовать |

## 3. Память

Пока игра идёт (снимать несколько раз: через минуту, через 10 минут, на поздних волнах):

```sh
adb shell dumpsys meminfo com.bimbleguard.app
```

Смотреть строки `TOTAL PSS` (сколько всего), `Native Heap`, `Graphics` и `Private Dirty`.
Здоровая игра держит примерно 250–400 МБ и не растёт от волны к волне. Если `TOTAL PSS`
монотонно растёт на сотни МБ — утечка (пришлите три снимка с отметкой волны). Для сравнения:
`adb shell cat /proc/meminfo | head -5` (общая и свободная память телефона).

## 4. Кадры и троттлинг

```sh
adb shell dumpsys gfxinfo com.bimbleguard.app
adb shell dumpsys gfxinfo com.bimbleguard.app reset      # обнулить счётчики перед замером
```

В выводе: `Total frames rendered`, `Janky frames` (процент), `90th/95th/99th percentile`.
Игра рисует через OpenGL ES (Compatibility), поэтому часть строк может быть пустой —
тогда ориентируйтесь на оверлей из раздела 5.

Перегрев и троттлинг процессора: `adb shell dumpsys thermalservice | head -30` и
`adb shell dumpsys battery | grep temperature` (в десятых долях градуса).

## 5. Оверлей диагностики в самой игре (без кабеля)

Скрыт по умолчанию. Включение: **Настройки (шестерёнка) → пять быстрых тапов по строке
версии** (надпись получит пометку `[diag]`). Те же пять тапов выключают его.
В бою в левом верхнем углу появится:

```
FPS 58  frame 17.2 ms (max 40)
mem 120 MB  vram 52 MB  draws 130
nodes 1200  orphans 0
enemies 80  towers 14  shots 6
step 0.9 ms  slow frames 0  dropped 0
quality notch 0/4
```

- `frame`/`FPS` — реальное время кадра; `max` — самый долгий кадр за полсекунды.
- `mem` — память движка (Godot), `vram` — видеопамять, `draws` — вызовы отрисовки (цель < 100).
- `nodes` и `orphans` — число узлов и «осиротевших» узлов. Если растут от волны к волне — утечка.
- `step` — сколько миллисекунд заняли шаги симуляции за последний кадр; `slow frames` — сколько
  кадров не уложились в бюджет шагов (22 мс), `dropped` — сколько шагов пришлось пропустить
  (игра замедлилась, но не зависла).
- `quality notch` — на сколько ступеней автозащита понизила графику (см. ниже).

**Записка о прошлом запуске.** Каждые 5 секунд боя игра пишет файл `user://last_session.json`
(уровень, волна, число врагов, память, FPS) и при организованном выходе (на карту, закрытие)
помечает его. Если прошлый запуск закончился не так, первой строкой оверлея будет:

```
prev run ended in battle: level 3 wave 41 enemies 220 mem 310 MB fps 12
```

- `battle` — процесс умер во время боя на переднем плане (вылет или нехватка памяти);
- `background` — игру свернули, а потом её не стало (система убила в фоне либо смахнули
  из списка приложений).

Цифры в строке — последнее, что игра успела записать (до 5 секунд назад).

Отладочная сборка (не релиз) позволяет достать файлы напрямую:
`adb shell run-as com.bimbleguard.app cat files/last_session.json` (в релизной сборке `run-as`
не работает — используйте оверлей).

### Строка «prev exit» (причина гибели прошлого запуска, Android 11+)

При старте игра спрашивает у Android (`ActivityManager.getHistoricalProcessExitReasons`), чем кончился
прошлый запуск, и показывает в оверлее строку:

```
prev exit: LOW_MEMORY rss=612 MB pss=420 MB FOREGROUND (low_memory)
prev exit: SIGNALED/9 rss=540 MB pss=390 MB FOREGROUND (probable_low_memory)
```

- Причины (`ApplicationExitInfo.REASON_*`): `LOW_MEMORY` — система убила процесс из-за нехватки памяти;
  `SIGNALED/9` (SIGKILL без причины) — **вероятное убийство по памяти** на телефонах, где Android
  не сообщает `LOW_MEMORY` (до Android 14 так почти всегда; на Xiaomi/HyperOS тоже бывает убийство
  «оптимизатором»); `CRASH` / `CRASH_NATIVE` — исключение Java / падение в нативном коде;
  `ANR` — приложение не отвечало; `EXIT_SELF`, `USER_REQUESTED` — обычный выход.
- `rss`/`pss` — память процесса на момент смерти (МБ), слово после — важность процесса
  (`FOREGROUND`, `VISIBLE`, `CACHED`…). Убийство в фоне (`CACHED`) — нормальная работа системы и
  **не** считается проблемой игры.
- Если прошлый запуск был убит по памяти / упал / завис **при игре**, игра понижает стартовое
  качество: 1-й раз подряд — ступень 2 (тени и MSAA выкл.), 2-й — 3, 3-й и далее — 4 (см. раздел 6).
  Счётчик подряд идущих плохих запусков сбрасывается после нормального выхода или запуска, прожившего
  10+ минут. Состояние: `user://exit_reasons.cfg`.
- На Android < 11 и на компьютере строки нет.

## 5a. Отчёты о сбоях в Firebase (Crashlytics)

Включено в Gradle-сборках («Android Play (AAB)», «Android Debug (Gradle)»); обычный APK «Android»
без Gradle отчётов не шлёт. Игрок может отключить: Настройки → «Отправлять отчёты о сбоях».

- **Где смотреть**: Firebase Console → проект `bimbleguard` → Release & Monitor → **Crashlytics**.
  Вкладка Dashboard — сводка, Issues — группы сбоев (по стеку). Откройте проблему: ниже «Keys»
  (уровень `level`, режим `mode`, сложность `difficulty`, пресет дня `daily_preset`, волна `wave`,
  ступень качества `quality_notch`, пик памяти `peak_mem_mb`, и для прошлого запуска
  `prev_exit_reason`, `prev_exit_kind`, `prev_exit_rss_mb`…), «Logs» (хлебные крошки: старт боя,
  каждая 5-я волна, смена качества, выход из боя) и «Device» (модель, ОС, память, свободное место).
- **Убийство по памяти Crashlytics не видит** (процесс убит сигналом без обработчика): такие запуски
  приходят как **non-fatal** «prev exit: LOW_MEMORY … / SIGNALED/9 …» **при следующем запуске**
  (все такие non-fatal сгруппированы в одну проблему: различайте по Keys и тексту).
- Нативные падения (Godot/драйвер GPU) приходят как fatal; **символы не загружаются**
  (`nativeSymbolUploadEnabled false`), стек будет из адресов в `libgodot_android.so`
  (можно сопоставить вручную с `libgodot_android.so` из `android_source.zip`/шаблона). Достаточно для
  группировки по модели и GPU.
- **Android vitals**: Play Console → приложение → Quality → Android vitals → Crashes and ANRs: сводка
  вылетов и ANR от Google без SDK, по моделям телефонов (только у установок из Play). Есть и «Excessive
  wakeups», «Stuck wake locks», «Startup time».
- Первый отчёт приходит после **следующего** запуска; Dashboard обновляется с задержкой в минуты.
- Что не пишем: uid, почту, ник (в ключах и логах). `user id` — только случайный хеш (если задан).
- Проверка на телефоне (не выполнялась агентом): установить «Android Debug (Gradle)», вызвать
  вылет (например, убить процесс командой `adb shell am crash com.bimbleguard.app`
  — это Java-исключение, попадёт в Crashlytics), открыть игру снова и ждать отчёт в консоли.

## 6. Автозащита от низкого FPS

Если средний кадр дольше 30 мс (меньше ~33 FPS) в течение 2 секунд, `QualityGuard` ступенчато
(раз в 5 секунд) понижает только картинку, не трогая правила игры и воспроизведение:

1. выключает тени солнца;
2. выключает MSAA;
3. эффекты на уровень «минимум» (числа урона, вспышки, частицы);
4. выключает эффекты совсем.

Выбор игрока в настройках не меняется; достигнутая ступень действует до закрытия игры.
Отдельно часы симуляции больше не «копят долг»: если шаги кадра дольше 22 мс, лишние шаги
отбрасываются, и игра идёт медленнее, а не зависает.

## 7. Что прислать разработчику

1. Модель телефона, версию Android, объём RAM.
2. `crash.txt` и `run.txt` из раздела 2 (или фото первой строки оверлея «prev run ended in…»).
3. Два-три снимка `dumpsys meminfo` с отметкой, на какой волне какого уровня сняты.
4. Был ли включён ×2, режим осады / «Испытание дня» / кооператив, и сколько минут шла игра.

## 8. Для разработчика: синтетические замеры на компьютере

- `tools/soak_test.gd` — бот играет долгий бой; CSV с ростом памяти и временем кадра
  (`LEVEL=3 MINUTES=30 godot --path . --resolution 960x540 --script res://tools/soak_test.gd`).
- `tools/soak_reload.gd` — многократный заход на уровень и возврат на карту (утечки между уровнями).
- Результаты и выводы: `docs/SOAK_REPORT.md`.

## Строка устройства и качество графики (2026-10-17)

Оверлей диагностики (5 тапов по версии в настройках) показывает строку `GPU | ОЗУ | окно dpi Гц | safe l,t,r,b`
и `quality notch N/4 tier <выбранный> (detected <найденный>)`. Присылайте её вместе с отчётом о тестировании
(`docs/DEVICE_TEST_CHECKLIST.md`). Выбор «Качество графики» (авто/низкое/среднее/высокое) — Настройки -> Общие.
