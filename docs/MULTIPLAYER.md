# Мультиплеер Bimbleguard: исследование и план (Firebase Spark, без серверов)

Статус: **исследование и план, код игры не менялся.** Дата проверки квот и документации:
**2026-10-14** (по официальным страницам firebase.google.com, ссылки в конце).
Всё, что не удалось подтвердить официальным источником, помечено **[не проверено]** или
**[оценка]**.

## 0. Резюме

1. **Spark тянет мультиплеер только малого масштаба**, и главный потолок не «число
   игроков», а *суточные квоты*: Firestore 50 000 чтений и 20 000 записей в сутки, RTDB
   100 одновременных соединений и 10 ГБ/мес (≈ 333 МБ/сутки) исходящего трафика.
2. **Без Cloud Functions нельзя ничего проверить на сервере.** Любой анти-чит —
   клиентский (детерминированный реплей, проверяемый другими клиентами) плюс то, что
   умеют Security Rules (время `request.time`, монотонность, размеры, разовая запись).
3. **Рекомендуемая последовательность:** этап 0 (рекорды + «призрак» плана постройки,
   Firestore) → этап 1 (daily seed и коды-челленджи, Firestore) → этап 2 (кооператив на
   2 игрока, lockstep через RTDB: SSE на приём + REST на отправку) → этап 3 (P2P WebRTC)
   — **этап 3 я рекомендую не делать**: WebRTC на Android требует GDExtension
   (противоречит `CLAUDE.md`), а бесплатный TURN без своего сервера практически
   недоступен (см. §6.4).
4. **Симуляция сейчас не детерминирована** (§7): геймплей завязан на переменный
   `delta` в `_process`, `Timer`/`create_timer`/`Tween`, физику Godot (`CharacterBody3D`
   героя), порядок групп узлов и `randf()` у жителей. Сначала нужен рефакторинг
   «симуляция на фиксированном тике, отдельно от вида» (§8) — он же нужен для реплеев и
   пойдёт на пользу тестам.
5. **Этап 0 можно начинать сразу**, без рефакторинга: ранжирование по волнам уже есть
   (`Online.submit_record`), а «призрак» в виде полупрозрачных башен по журналу команд
   не требует детерминизма.

## 2. Как делают такие игры (обзор подходов)

| Подход | Примеры | Нужен сервер? | Подходит нам? |
|---|---|---|---|
| Таблицы рекордов + проверка | Bloons TD 6 (ежедневные/гоночные события), Kingdom Rush (только офлайн) | Для честного топа — да | Да, этап 0, анти-чит ограниченный |
| Асинхронный «призрак» (реплей лучшего игрока) | гонки; Clash Royale — просмотр реплеев | Хранилище | Да; для TD «призрак» = журнал команд |
| Асинхронные PvP (защита против чужой базы) | Clash of Clans, Guns Up! | Да, с серверной проверкой | Нет: проверять результат негде |
| Ежедневный сид / челлендж по коду | Slay the Spire daily, Spelunky daily | Минимальный (общее время и таблица) | **Да, этап 1** |
| Кооператив через P2P, прокси через облако | **Bloons TD 6**: 2–4 игрока, общие деньги от лопанья шариков делятся поровну, у каждого свой герой; соединение P2P, проксировано через Cloudflare (по данным вики Bloons) | Фактически да (прокси/матчмейкинг) | Идея кооператива — да, транспорт — через RTDB |
| Детерминированный lockstep: по сети только команды | RTS (Age of Empires), Clash Royale (по описаниям разработчиков, **[не проверено]** у Supercell) | Реле или P2P | **Да, этап 2**, команды TD редкие |
| Серверная авторитарная симуляция | большинство MMO | Да | Невозможно на Spark без Functions |

Ключевая идея для нас: **tower defense идеален для lockstep по сети** — игрок редко
подаёт команды (построить/улучшить/продать, приказ герою), а всё остальное (волны, враги,
башни, снаряды) считается из seed. Трафик — десятки байт в секунду. Цена — строгий
детерминизм (Gaffer On Games, «Deterministic Lockstep»).

| Auth | 50 000 MAU; **100 новых аккаунтов в час с одного IP** | Отдельной квоты на анонимов нет; 100 млн анонимных аккаунтов максимум |

| Hosting | 10 GB, 360 MB/сутки | Можно для страницы-редиректа ссылок, но не обязательно |

Что уточнить на практике:
- **[не проверено]** что именно происходит при исчерпании квоты на Spark (по документации
  Firestore запросы отклоняются до сброса; отдельного описания RTDB нет) — клиент обязан
  корректно обрабатывать ошибки и переходить в офлайн.
- **[не проверено]** учитываются ли чтения, выполненные самими правилами (`get()`,
  `exists()`) — да, как чтения документов; `resource.data` в правилах дополнительных
  чтений не создаёт. Лимит: 10 вызовов `get/exists` на запрос.
- **[не проверено]** доступность TTL-политик Firestore (авто-удаление старых челленджей)
  на Spark; запасной вариант — владелец сам удаляет свои документы (лимит 20 000
  удалений/сутки).

### 3.1 Listen/SSE из Godot

- **RTDB REST поддерживает стриминг**: заголовок `Accept: text/event-stream`, события
  `put`, `patch`, `keep-alive`, `cancel`, `auth_revoked`, следовать редиректам 307, токен
  в параметре `auth` ([RTDB REST](https://firebase.google.com/docs/database/rest/retrieve-data)).
  Одно такое соединение = 1 из 100 одновременных (тексты биллинга: «включая server-sent
  events»).
- **Firestore REST «слушать» не умеет** в документированном виде: страница про REST API
  не описывает listen и рекомендует RPC (gRPC); официального описания listen для REST
  найти не удалось **[не проверено]**. Значит, **для Firestore только polling** (`runQuery`,
  `get`), и каждый опрос стоит чтений. Для живого обмена Firestore не годится.
- **Godot**: `HTTPRequest` накапливает ответ целиком и для SSE непригоден. Нужен
  низкоуровневый `HTTPClient` (`connect_to_host` с TLS, `request`, `poll()`,
  `read_response_body_chunk()`), обработка 307, разбор потока `event:/data:`,
  переподключение с backoff и таймаут «нет keep-alive 60 с» **[интервал keep-alive в
  документации не указан — замерить в прототипе]**. Токен живёт ~1 час: по `auth_revoked`
  переподключиться с обновлённым (`Online._ensure_auth` уже обновляет токен).
- **Важная ловушка трафика:** каждый TLS-хэндшейк ≈ 3,5 КБ скачанного (страница
  биллинга RTDB). Отдельный `HTTPRequest` на каждую запись = лишние килобайты каждые
  доли секунды. Писать нужно **одним постоянным `HTTPClient` с keep-alive** и пачками.

## 4. Расчёт: сколько влезает в Spark

Допущения явно обозначены; **все цифры — [оценка]**, перед релизом их нужно замерить
счётчиками в прототипе (§8, R6).

### 4.1 Этапы 0–1 (Firestore)

Бюджет на игрока в день (DAU), «умный» клиент: топ-10 запрашивается при открытии экрана,
результат кэшируется на 10 минут.

| Действие | Чтения | Записи |
|---|---|---|
| Открыть таблицу рекордов уровня (топ-10) ×3 | 30 | 0 |
| Открыть призрак/реплей лидера ×2 | 2 | 0 |
| Отправить рекорд осады ×1–2 | 0 | 1–2 |
| Daily: таблица топ-20 ×1 + отправка | 20 | 1 |
| Облачное сохранение/загрузка | 1 | 1 |
| **Итого** | **≈ 55** | **≈ 3–4** |

- Узкое место — **чтения**: 50 000 / 55 ≈ **900 DAU**; с агрессивным кэшем (топ-10 раз в
  30 мин, топ-20 daily по запросу) ≈ 30 чтений → **≈ 1 600 DAU**.
- Записи: 20 000 / 4 ≈ 5 000 DAU — не проблема.
- Хранение: рекорд-документ ≈ 0,3 КБ + реплей ≈ 10–30 КБ **только у одного документа на
  игрока на уровень**; 1 GiB / 30 КБ ≈ 35 000 реплеев — не проблема.
- Исходящий трафик Firestore 10 GiB/мес: 30 КБ × 2 просмотра × 1 000 DAU × 30 дней ≈
  1,8 ГБ — запас есть.
- 100 новых аккаунтов/час с IP — для мобильных операторов с общим NAT может ударить в
  пик установок; повторный вход использует сохранённый `refresh_token` (уже есть в
  `Online`).

### 4.2 Этап 2 (кооператив через RTDB)

Модель: каждый игрок держит **1 SSE-соединение** на комнату (слушает команды партнёра) и
пишет REST-запросами по постоянному соединению. Лобби (поиск комнаты) — опрос REST, он
**не занимает соединений**.

- **Соединения:** 100 / 2 = **максимум 50 матчей одновременно**; с запасом на лобби и
  отладку — 40–45 матчей.
- **Трафик (скачивание, платный):** событие с командой ≈ 120 Б данных + рамка SSE/TLS ≈
  250 Б; подтверждение тика («у меня всё до тика T») 2 раза в секунду ≈ 200 Б. На игрока
  ≈ 0,4–0,6 КБ/с → 15-минутный матч ≈ 0,4–0,5 МБ на игрока, **≈ 1–2 МБ на матч с
  запасом на лобби и переподключения**.
- Суточный бюджет ≈ 333 МБ → **≈ 160–330 матчей в сутки, то есть 300–650 игроков-матчей
  в сутки**; при 10 ГБ/мес вся арифметика сходится: 10 ГБ / 1,5 МБ ≈ 6 600 матчей в
  месяц.
- Пиковая нагрузка: 330 матчей/сутки, сконцентрированных в 6 вечерних часов, → ≈ 55
  матчей/час → одновременно ≈ 14 матчей (при 15 мин) — **по соединениям запас ×3**.
- Вывод: **кооператив рассчитан на закрытое/небольшое сообщество (сотни игроков в
  день)**, а не на массовый запуск. Если квота исчерпана, функцию нужно отключать
  автоматически и честно говорить игроку.
- Тот же проект Firebase используется Firestore-частью: квоты RTDB и Firestore
  независимы, но 100 соединений общие для всех пользователей RTDB, включая стриминг
  лобби — поэтому лобби опросом, а не SSE.

### 4.3 Этап 3 (P2P)

Трафик через Firebase почти исчезает (только сигналинг ≈ 5–10 КБ на матч), остаётся
проблема NAT/TURN, см. §6.4.

### 5.1 Формат журнала команд (одинаков для реплея, daily, челленджа и кооператива)

Заголовок: `{v: sim_version, balance_hash, level, mode, seed, perks_hash, players: n}`.
Команды: `{tick: int, player: int, type: enum, args}`, где `type` ∈

| Команда | Откуда в коде сейчас |
|---|---|
| `build(slot, tower_type)` | `BuildManager.build_on` (build_manager.gd:105), вызывается из `main._execute` (main.gd:387) |
| `upgrade(slot)` | `BuildManager.upgrade` (build_manager.gd:124) |
| `sell(slot)` | `BuildManager.sell` (build_manager.gd:134) |
| `sword`, `repair` | `main._on_command_pressed` (main.gd:347–370) |
| `trade(lots)` | `Villagers.sell` через `main._on_command_pressed` |
| `move_to(x, z)` | `Hero.move_to` (hero.gd ~121) |
| `joystick(vec)` (квантованный, только при изменении) | `hero.joystick_vector` |
| `attack`, `spin` | `Hero.try_attack` (hero.gd:156), `try_spin` (hero.gd:171) |
| `speed(1\|2)`, `pause` | `main._toggle_speed` (main.gd:197), `_toggle_pause` (main.gd:183) |

Сжатие: бинарный формат (`PackedByteArray`), `compress(ZSTD)`, затем base64 для
хранения строкой. **[оценка]** 20 минут игры ≈ 600 команд + джойстик 5 Гц с дельтами ≈
10–30 КБ после сжатия, что << 1 MiB лимита документа. Стоит ограничить размер правилом
(`size() < 60000`).

### 5.2 Firestore (этапы 0–1)

```
leaderboards/level_{id}/scores/{uid}   {name, wave, updated, simv}          — уже есть
replays/level_{id}/runs/{uid}          {wave, simv, blob (строка base64), updated}   — этап 0
daily/{yyyymmdd}/scores/{uid}          {name, wave, stars, blobRef?, updated}
challenges/{code}                      {level, seed, mutators, ownerName, ownerWave, created}
challenges/{code}/results/{uid}        {name, wave, updated}
flags/{level}/{uid}/by/{flagger}       {reason, updated}                   — жалобы (§9)
```

Правила (идея, к существующему `firestore.rules`):
- рекорд только растёт (уже есть) + `simv` совпадает с актуальной версией;
- `daily/{day}/scores/{uid}`: запись только если `day` == сегодня по `request.time`
  (`request.time.year()/month()/day()`), то есть клиент с неверными часами не может
  писать «в чужой день»; один документ на игрока, рекорд только растёт;
- `challenges/{code}`: `create` только если `resource == null`, поля неизменяемы после
  создания (`allow update: if false`), код 6–8 символов — коллизии отсекает
  `resource == null`;
- ограничения размера строк (`blob.size() < 60000`, `name.size() <= 16`);
- **правило «минимально возможного времени»** (дешёвый анти-чит, 1 чтение на запись):
  при старте забега клиент пишет `runs/{uid} {startedAt: request.time, level}`; рекорд
  для волны `w` допустим, только если
  `request.time - get(runs/uid).startedAt >= (first_delay + (w-1)*wave_duration)/2`
  (÷2 — ускорение ×2). Работает потому, что волны идут по фиксированным часам
  (`wave_manager.gd:101`, `_next_wave_timer.start(plan.wave_duration)`), раннего вызова
  волны нет. Нельзя «отправить волну 5000 за секунду», но можно отправить честную по
  времени, нереальную по защите волну → поэтому нужен §9.

Daily seed: `seed = hash("tg-" + yyyymmdd)` — чистая функция даты, на сервере ничего не
храним. Дата берётся из **заголовка `Date` ответа Firebase** (а не из часов телефона), а
запись в daily всё равно проверяется правилами по `request.time`.

### 5.3 RTDB (этап 2)

```
rooms/{roomId}/meta          {host: uid, level, seed, simv, created, state}   — host пишет один раз
rooms/{roomId}/players/{uid} {name, slot: 0|1, ready}                          — только свой узел
rooms/{roomId}/cmds/{uid}/{n} {t: tick, d: base64(бинарная пачка)}             — только свой uid, n по возрастанию
rooms/{roomId}/ack/{uid}      {t: tick, h: crc32 состояния}                    — подтверждение и хэш
lobby/{level}/{roomId}        {host, name, created}                            — публичные комнаты (опрос)
```

Правила (набросок): запись в `cmds/{uid}` и `ack/{uid}` только при
`auth.uid == $uid` и если uid числится в `players`; `.validate` на размер
(`newData.val().length < 400`); узел `meta` пишется один раз (`!data.exists()`);
второй игрок занимает слот только если он свободен (`!data.exists()` на
`players/$uid` и ровно 2 игрока); `created <= now`. Приглашение по **коду комнаты**
(4–6 символов) проще лобби и не требует опроса — делаем первым.

Транспорт: SSE на `rooms/{id}/cmds/{partner_uid}` (+ `ack`), запись — одним `HTTPClient`
с keep-alive, пачки раз в 200–250 мс и только если есть что слать (иначе «тишина»
подтверждается `ack` раз в 500 мс).

### 5.4 Схема lockstep (этап 2)

1. Единый `seed`, `simv`, `balance_hash`, уровень — в `meta`; клиенты сверяют `balance_hash`
   (иначе «версии не совпадают»).
2. Симуляция идёт на **фиксированном тике 30 Гц**; команды применяются с задержкой
   `D` тиков (старт `D = 15` ≈ 0,5 с, чтобы покрыть RTT REST ≈ 100–300 мс **[оценка]**),
   порядок применения на одном тике: сортировка по `(tick, player, seq)`.
3. Клиент не симулирует тик `T`, пока не получил от партнёра пачку или `ack` с
   `t >= T` («стоп-кадр» ожидания, UI «ждём напарника»).
4. Каждые N тиков (например, 60) обмен **хэшем состояния** (золото, дерево, жизни,
   число врагов, сумма `progress`, сумма HP, состояние башен). При расхождении — показать
   «рассинхрон», хост шлёт снимок (≈ 1 КБ на 100 врагов) или матч завершается.
5. Отключение: через 10 с тишины — «ждём…», через 30 с — завершить матч с сохранением
   результата как «одиночный».
6. Кооперативные правила (дизайн, обсуждать отдельно): общие жизни замка, общее золото
   (проще) или «деньги от убийств делятся пополам, как в BTD6», у каждого свой герой и
   своё дерево.

## 6. Эксперименты с транспортом и NAT

### 6.1 RTDB как реле — выбранный вариант
Плюсы: работает через любой NAT, одна точка отказа (Firebase), правила безопасности,
анонимный Auth уже подключён. Минусы: задержка 100–300 мс на хоп, 100 соединений, 10 ГБ.

### 6.2 Firestore как реле — не подходит
Нет listen по REST → polling: 2 игрока × 2 опроса/с × 900 с = 3 600 чтений на матч;
квота 50 000/сутки ≈ **14 матчей в день**. Только лобби и результаты.

### 6.3 ENet (встроен в Godot, без плагинов)
UDP напрямую; нужен доступный адрес. У мобильных операторов CGNAT, hole punching в
Godot нет, UPnP работает на домашних роутерах. Годится только для **локальной сети /
Wi-Fi-раздачи** («играть рядом»). Это возможная дешёвая опция для друзей в одной сети,
сигналинг не нужен (сканирование/ввод IP).

### 6.4 WebRTC P2P (этап 3)
- В Godot 4 `WebRTCPeerConnection` на **не-web платформах требует внешнего GDExtension
  `webrtc-native`** ([документация Godot](https://docs.godotengine.org/en/stable/tutorials/networking/webrtc.html))
  — нарушает правило «никакого GDExtension» из `CLAUDE.md`; нужно письменное решение
  владельца.
- Сигналинг можно положить в RTDB (`rooms/{id}/signal/{uid}`: SDP offer/answer, ICE) —
  тот же SSE+REST, ≈ 5–10 КБ на матч.
- STUN бесплатный: `stun.cloudflare.com` (бесплатный и без лимита по документации
  Cloudflare); публичные STUN-серверы Google тоже существуют **[не проверено сегодня]**.
- **TURN — главная проблема.** Доля соединений, которым нужен ретранслятор, на мобильных
  сетях заметна **[оценка: порядка 10–20 %, зависит от операторов]**. Бесплатные варианты:
  - **Cloudflare Realtime TURN**: 1 000 ГБ/мес бесплатно, потом 0,05 $/ГБ, самообслуживание
    через банковскую карту. Учётные данные выдаются вызовом API с секретным токеном —
    «в вашем бэкенде или Cloudflare Workers» (из FAQ), то есть **нужен мини-сервер/Worker**
    (противоречит условию «без своих серверов»); зашить секрет в APK нельзя (его извлекут,
    а перерасход спишут с карты владельца).
  - **Metered Open Relay**: заявлено 20 ГБ/мес, но общие публичные креды ненадёжны, нужен
    API-ключ **[не проверено, источники противоречат]**.
  - **Xirsys** free: ≈ 500 МБ/мес TURN, **ExpressTURN**: заявлено 1 ТБ **[не проверено]**.
  - Свой coturn — это уже свой сервер.
- **Вывод: P2P даёт экономию квот RTDB, но добавляет GDExtension + TURN-риск.** Этап 3
  стоит делать только если (а) RTDB-квот реально не хватает и (б) владелец разрешил
  GDExtension. Иначе — остаёмся на этапе 2.

## 7. Аудит детерминизма текущего кода

Итог: **геймплей сейчас не детерминирован**, но хорошая новость — **в самой боевой
логике нет случайности**: `WavePlan.spawns` (wave_plan.gd) чисто детерминирован,
башни берут ближайшего врага, урон не бросает кубики. Недетерминизм создают время,
физика, порядок и визуальные `randf()`.

### 7.1 Случайность (RNG)

| Место | Что | Влияет на геймплей? |
|---|---|---|
| `enemy.gd:35` `anim_phase = randf()` | фаза анимации | Нет (вид), **но тратит общий поток `randf()`** — любой будущий геймплейный `randf()` разъедется. Нужны отдельные `RandomNumberGenerator` для sim и для вида |
| `villager.gd:42–44, 91, 98–100` | старт анимации, поворот, паузы и точка прогулки | **Да, косвенно**: от позиции жителя зависит `trade_reach` (villagers.gd) → карточка торговли; решение: стоять в фиксированной точке при торговле или вести прогулку на sim-RNG |
| `wood_tree.gd:41, 126` | поворот ствола | Нет (вид) |
| `looping_model.gd:17` | сдвиг анимации | Нет |
| `lightning_fx.gd:22–24` | дрожание молнии | Нет |
| `one_shot_fx.gd:31`, `tower_model.gd:40` | высота тона звука | Нет |
| `main.gd:920` `tips.pick_random()` | совет на экране | Нет |
| `villagers.gd:69` `sort_custom` | выбор домов, сортировка по `score` | Косвенно: сортировка Godot **нестабильна**, при равных очках порядок не гарантирован → добавить второй ключ (x, z) |
| Daily seed / мутаторы | пока не существуют | Новые, будут идти от `RandomNumberGenerator(seed)` |

`RandomNumberGenerator` в Godot — PCG32, при одинаковых seed и порядке вызовов выдаёт
одинаковые числа **[по наблюдениям сообщества, сверить с исходниками версии]**; чтобы
не зависеть от смены версий движка, для sim можно написать свой xorshift/PCG на `int`
(10 строк).

### 7.2 Время и `delta`

| Место | Проблема |
|---|---|
| `enemy.gd:86–93` `_process(delta)`: `progress += speed * _slow_factor * delta` | Шаг зависит от длительности кадра; результат отличается на 30 и 60 FPS и при `time_scale` ×2 |
| `wave_manager.gd:39–55` спавн по `spawner["left"] -= delta` | За кадр спавнится **не более одного** врага; при больших `delta` (просадка FPS) очередь отстаёт; момент спавна зависит от кадров |
| `wave_manager.gd:33, 86, 101` `Timer` | Старт волн по `Timer` (idle-обработка, момент срабатывания зависит от кадра) |
| `tower.gd:41–51` `_cooldown` на `delta`; `retarget_interval` 0,15 с | Момент выстрела зависит от кадров; `retarget_interval` — ещё один «таймер на delta» |
| `projectile.gd:46–66` самонаводящийся: `step = speed * delta`, попадание по `length() <= max(step, hit_distance)` | **Момент попадания зависит от кадра** → кто добьёт врага, награда, сплит слизня |
| `projectile.gd:69–90` дуга: `_time += delta` | Аналогично |
| `hero.gd:165` `create_timer(attack_hit_delay)` → `_strike` (hero.gd:245) | Удар героя по таймеру SceneTreeTimer (кадровая точность) |
| `hero.gd:90–119` `_physics_process` и `Input.*` | Ввод напрямую из `Input`, не из команд; `move_and_slide()` — **физика Godot** |
| `wood_tree.gd:99, 117, 124, 132` `Tween` + `create_timer` | Состояние дерева (`_hits_left`, регроу) зависит от твинов/таймеров — влияет на добычу дерева |
| `enemy.gd:193`, `main.gd:797`, `hero.gd:179` `Tween` | Вид, но есть места, где геймплей ждёт твин — проверить `hero.gd:179` (вихрь: урон мгновенный, ок) |
| `main.gd:197–199` `Engine.time_scale` ×2 и `main.gd:183–187` `get_tree().paused` | Для кооператива и реплея нужны командами (`speed`, `pause`) и общими для всех |
| `main.gd:255, 725–728` `Time.get_ticks_msec` | Только вид — допустимо |
| `online.gd:66, 162` часы системы | Только сеть — допустимо |

### 7.3 Порядок обновления

- Все сущности обновляются в `_process` в порядке дерева; **порядок между башнями,
  снарядами и врагами не закреплён** — при одновременных попаданиях разный порядок меняет,
  кто убил врага и в каком порядке сработают `died`/`split`.
- `get_nodes_in_group(Enemy.GROUP)` (tower.gd:73,132; projectile.gd:77; hero.gd:186,205,247,276)
  — порядок групп **не гарантируется документацией** (на практике — порядок добавления).
  `find_nearest_enemy` берёт `<=` → при равных расстояниях выигрывает последний; нужен
  явный `id` врага и упорядочивание по `(distance_sq, id)`.
- Враг — `PathFollow3D` внутри `Path3D` (`progress` — скаляр, это хорошо), но позиция
  берётся из `global_position` (сэмплирование `Curve3D`): годится для одного APK, но
  лучше считать расстояния по `progress` и таблице точек пути в sim.
- Слизень делится: `split.emit` в `take_damage` (enemy.gd) — порядок появления «половинок»
  влияет на `_remaining`; нужен явный `id` и порядок.

### 7.4 Числа с плавающей точкой и физика

- Игровая математика почти вся на `float` (в GDScript это 64-битный `double`, в
  `Vector3` — 32-битный `real_t`): `+ − × ÷` и `sqrt`
  по IEEE одинаковы на одном бинарнике (arm64 APK), расхождения возможны между
  архитектурами (x86-эмулятор/ПК/ARM) из-за компилятора (FMA) и библиотечных
  `sin/cos/pow`. **Для lockstep разрешить кооператив только между сборками одной
  версии и ABI (arm64-v8a)** и ввести хэш состояния (§5.4).
- `Vector3`-математика, `Curve3D`, `Path3D` — в одном бинарнике детерминирована.
- **Физика Godot** (`CharacterBody3D` героя, `intersect_shape` при построении сетки,
  `Area3D` слотов) для lockstep недопустима: порядок решения контактов и дробные
  допуски не гарантируются между машинами. `WalkGrid` (AStarGrid2D, клетка 0,5 м,
  `walk_grid.gd`) уже есть и даёт хорошую основу для **собственной кинематики героя на
  клетках**. Сетку строят запросами физики один раз после первого кадра — при
  одинаковой сцене результат одинаков, но в заголовок реплея стоит класть
  `hash(blocked_cells)` для контроля.

## 8. Что нужно переделать (рефакторинг)

Порядок важен; каждый шаг — отдельный коммит по правилу «по одному пункту ROADMAP».

- **R0. Журнал команд (без остального рефакторинга).** Класс `CommandLog` и
  `GameCommands.apply(cmd)`: все ввод-действия (§5.1) идут через один метод, который
  пишет в журнал и выполняет. Даёт «призрак» плана постройки (этап 0) и реплей
  на лету.
- **R1. Seed и RNG.** `SimRng` (свой PCG на `int`); отделить RNG вида. Убрать
  геймплейный `randf()` у жителей (фиксированные точки торговли).
- **R2. Фиксированный тик.** Весь геймплей в `_physics_process` (дельта фиксирована; при
  `time_scale` ×2 просто больше тиков **[проверить на 4.3]**) или в собственном
  `Sim.step()` с целочисленным `tick`. Кулдауны/таймеры/регроу/удар героя/старт волн —
  счётчики тиков (`int`), без `Timer`, `create_timer`, `Tween` в геймплее (твины — только
  вид).
- **R3. Разделение sim и вида.** `EnemySim` (id, `progress`, hp, слоу, тип) в массиве, а
  `EnemyCrowd`/`Enemy` только рисуют; то же для снарядов (в sim — «заряд» с дистанцией,
  вид — полёт). Явные `id`, обход по возрастанию `id`, тай-брейки по `(dist, id)`; не
  использовать порядок групп.
- **R4. Герой без физики.** Кинематика по `WalkGrid` (клетки, столкновение со
  `blocked`); джойстик и тапы → команды `joystick`/`move_to`. `CharacterBody3D` остаётся
  только для вида/камеры или убирается.
- **R5. Хэш состояния и тест детерминизма.** `Sim.state_hash()`; тест: два прогона с одним
  журналом на 30 и 60 FPS дают одинаковый хэш (`tests/test_determinism.gd`, в
  `tests/run_all.sh`). Этот тест — «бюджет доверия» для всех этапов.
- **R6. Счётчики квот.** Debug-счётчики чтений/записей/скачанных байт (в `Online` и
  `RtdbStream`) и вывод в лог — чтобы заменить оценки из §4 реальными.
- **R7. Версионирование.** `SIM_VERSION` (int) и `balance_hash` (хэш `resources/*.tres`
  и `levels.json`); реплей с другой версией считается «устаревшим» (показывается только
  как статистика).
- Прочее: пауза и ×2 в кооперативе становятся командами; `Perks` попадают в заголовок
  (`perks_hash`) или отключаются в daily/кооперативе (честная стартовая позиция —
  рекомендуется).

## 9. Анти-чит без сервера

Нельзя защититься полностью; цель — «честность по умолчанию» и дешёвое выявление
очевидного.

1. **Правила Firestore:** монотонный рекорд, лимиты размера, привязка к `uid`, запись в
   daily только в «сегодняшний» день, минимально возможное время для волны (§5.2).
2. **Журнал + проверка на клиенте.** Рекорд отправляется вместе с журналом команд
   (реплей). Любой клиент, открывающий призрак из топ-10, **прогоняет реплей headless на
   ускорении** (30 мин игры ≈ секунды) и сверяет волну. Несовпадение → запись в
   `flags/{level}/{uid}/by/{flagger}`; запись скрывается из топа, если жалоб от 3+
   разных аккаунтов. Слабое место: жалобу может подделать злоумышленник с несколькими
   анонимными аккаунтами (100 аккаунтов/час с IP) — риск принят, это «лучшее
   возможное без сервера».
3. **Топ-N «подтверждён»:** показывать значок «проверен» только записям, реплей которых
   успешно прогнали 3 разных клиента (счётчик подтверждений — `verifies/{uid}/by/{flagger}`).
4. Без детерминизма (R1–R5) п. 2–3 невозможны: до них «проверка» ограничена п. 1.
5. Подмена часов: daily проверяется по `request.time` в правилах (не по часам телефона).

| Лишний трафик из-за хэндшейков | Средняя | одно keep-alive соединение, пачки |
| Накрутка рекордов / ботофермы | Высокая для топа | §9; «подтверждён» только с проверками; открыто говорить, что топ неофициален |
| Обновление баланса ломает реплеи | Высокая | `SIM_VERSION`, `balance_hash`, сезоны |
| 100 аккаунтов/час с IP при вирусном росте | Низкая | `refresh_token` сохраняется; запрос повышения квоты в консоли |
| Исчерпание сроков из-за рефакторинга | Высокая | R0–R1 дают ценность сразу; этапы 0–1 не ждут R2–R5 |
| Приватность / Data safety (Google Play) | Низкая | в анкету добавить «ник» и «журнал игровых действий»; реплей не содержит личных данных |
| `CLAUDE.md` запрещает мультиплеер/GDExtension | Фиксированный | §1: решение владельца до этапа 2 |

## 12. Открытые вопросы владельцу

1. Разрешить ли мультиплеер (этап 2) в `CLAUDE.md` и каков целевой масштаб (друзья /
   сотни игроков в день)? Spark даёт именно этот порядок.
2. Кооператив: общие жизни/золото или раздельные (как в BTD6)?
3. Разрешить ли GDExtension `webrtc-native` (этап 3)? Рекомендация — нет.
4. Допустимо ли включить в проект Firebase второй сервис (RTDB) и его правила?
5. Нужна ли привязка «настоящего» аккаунта (Google Sign-In) для переноса прогресса?
   Анонимный `uid` теряется при переустановке (облако привязано к нему же).
