# Аккаунты, профиль, ник, онбординг, туториал

Статус: код написан (включая вход по почте) и проверен **headless-тестами с поддельным сервером** и правилами на
**локальном эмуляторе Firestore**. Вход и синхронизация на живом Firebase-проекте **не
проверялись** (проект не создан, см. `docs/FIREBASE.md`). Не считайте вход рабочим, пока не
пройден чек-лист оттуда.

Ограничения проекта: Firebase на плане **Spark — без Cloud Functions**; без секретов в
клиенте; без рекламы и аналитики; игра работает полностью офлайн и без `firebase.cfg`.

## Поток первого запуска

`boot.tscn` → (фоном `Online.start()`) → маршрут по сохранённому профилю (`Onboarding.route`):

1. нет ника или конфликт ника → экран ника (`nickname.tscn`);
2. ник есть, туториал не пройден (`tutorialVersionCompleted < TUTORIAL_VERSION`) → туториал
   на уровне 1 (`tutorial.gd`, реагирует на настоящие действия игрока);
3. иначе → карта мира.

Шаг выводится из профиля, поэтому после убийства приложения поток продолжается с того же
места, а повторный запуск ничего не меняет. Возвращающийся игрок не ждёт сеть.

## Профиль (`scripts/player_profile.gd`)

Локальный профиль лежит в `progress.cfg` (секция `[profile]`), облачный — `users/{uid}`:
`schemaVersion, onboardingCompleted, tutorialVersionCompleted, progression{unlocked, stars,
endless, perks}, settings{sound}, createdAt, updatedAt`. Ник в `users` **не хранится** — он
в `publicProfiles/{uid}`.

Слияние локального и облачного (`PlayerProfile.merge`): прогресс только растёт (максимум
звёзд/рекордов/открытых уровней), перки — от стороны, потратившей больше звёзд, настройки — от
более новой, флаги онбординга только вперёд. Запись в облако — условная (`updateTime`/
`exists:false`): при гонке с другим устройством читаем и сливаем заново (до 3 раундов).
Документ новой схемы никогда не перезаписывается старой версией игры (`newer`, «обновите
игру»).

## Вход (`scripts/auth_service.gd`)

- Гость: `accounts:signUp` без данных (анонимный uid). Refresh-токен хранится в
  зашифрованном файле (`session_store.gd`; ключ выводится из id устройства и соли в приложении — это обфускация, а не аппаратная защита: root-доступ его вскроет), не в `progress.cfg`; старые
  открытые токены из `[online]` мигрируют и стираются.
- Токен обновляется за минуту до истечения; повторы с задержкой для 429/5xx; регистрация не
  повторяется (чтобы не создать два аккаунта).
- Известный uid с недоступным (но не отвергнутым) токеном **не заменяется** новым гостем.
  Отвергнутый навсегда токен гостя → явный выбор игрока в «Профиле» («Новый гость»).
- Почта и пароль — см. раздел «Вход по почте» ниже. Вход через Google/Play Games невозможен
  без нативных плагинов (запрещены `CLAUDE.md`): `link_with_idp` честно отвечает
  `not_available`.
- Токены, почта, пароль и тела ответов нигде не печатаются (тест `_test_no_secret_logging`
  следит, что в коде аккаунтов нет `print`/`push_error`).

## Вход по почте (`AuthService` + `Online` + `EmailAuthDialog` + «Профиль»)

В консоли Firebase включены **Anonymous** и **Email/Password** (`docs/FIREBASE.md`). Все вызовы —
Identity Toolkit REST, без SDK и без Cloud Functions.

| Действие | Запрос | Что происходит |
|---|---|---|
| Привязать почту к гостю | `accounts:update` {idToken, email, password, returnSecureToken} | **uid и весь прогресс остаются**; аккаунт становится «email». |
| Войти на другом устройстве | `accounts:signInWithPassword` | Сессия переключается на uid аккаунта, локальный профиль **сливается** с облачным, затем синхронизация. |
| Забыли пароль | `accounts:sendOobCode` {requestType: PASSWORD_RESET, email} | Письмо от Firebase. Неизвестный адрес выглядит как успех (не раскрываем, кто зарегистрирован). |
| Выйти | локально | Сначала досинхронизация; без связи отказ «нужен интернет». Затем стираются сессия и локальные данные, игра идёт с загрузки. Гость выйти не может (единственная копия пропала бы). |
| Войти заново | то же `signInWithPassword` | Для аккаунта, который уже открыт: обновляет вход (нужно перед удалением, `CREDENTIAL_TOO_OLD_LOGIN_AGAIN`). Другой аккаунт при открытом email-аккаунте отклоняется (`other_account`): сначала выйти. |

Где в интерфейсе: «Профиль» (гость: «Привязать почту», «Войти по почте»; аккаунт с почтой:
«Войти заново», «Выйти из аккаунта») и, при первом запуске, на экране ника кнопка «У меня уже
есть аккаунт» (иначе новому устройству пришлось бы придумывать ник и проходить обучение, чтобы
добраться до Профиля). Без `firebase.cfg` всех этих кнопок нет.

### Слияние при входе на другом устройстве

1. Ждём текущую синхронизацию, на время переключения синхронизация блокируется.
2. `signInWithPassword` → новые токены, `account_type = email`, uid аккаунта; uid прежнего гостя
   запоминается в `previous_uid`.
3. Ник прежнего гостя принадлежит его uid, поэтому локальный ник сбрасывается; ник аккаунта
   приходит из `publicProfiles/{uid}`. Если у аккаунта ника нет — игрока попросят выбрать.
4. Обычная синхронизация (`PlayerProfile.merge`): звёзды, рекорды и открытые уровни — максимум,
   перки — от стороны, потратившей больше звёзд, настройки — от более новой, флаги онбординга
   только вперёд. Результат пишется в аккаунт (условная запись, до 3 раундов).
5. Если связи нет прямо после входа, вход всё равно состоялся; профиль досинхронизируется позже
   (`synced: false`, статус «Не синхронизировано»).

Ограничения:

- Прогресс гостя этого устройства **добавляется** к аккаунту (по максимуму); обратно
  «разделить» нельзя. Для общего устройства: выйдите из аккаунта перед передачей.
- Осиротевший гость остаётся в Authentication и в Firestore (`users`, `publicProfiles`,
  `nicknames`) и держит свой ник. Автоочистка потребовала бы удалять его по токену до входа;
  не сделана. Такие аккаунты бесплатны, ручная чистка — в консоли.
- Выход не отзывает токен на сервере (REST-клиент не может): токен просто удаляется с устройства.
- Почту в клиенте не храним и не показываем (после привязки известен только тип «email»).
- Пароль существует только в поле ввода и аргументах вызова: на диск (`progress.cfg`,
  `session.dat`) не пишется, поле очищается при успехе и закрытии, у поля отключены копирование
  и контекстное меню.
- Сброс пароля письмом работает только для адресов, зарегистрированных в Firebase; ссылка из
  письма открывается в браузере, возврата в игру нет (после смены пароля войдите в игре).

### Ошибки и сообщения (`EmailRules.message`)

| Код Firebase | Ключ | Игрок видит |
|---|---|---|
| `EMAIL_EXISTS`, `CREDENTIAL_ALREADY_IN_USE` | `credential_in_use` | «Эта почта уже занята… нажми «Войти по почте»» (автослияния нет) |
| `WEAK_PASSWORD` (и клиент < 6 символов) | `weak_password` | «Пароль слишком простой: минимум 6 символов…» |
| `INVALID_LOGIN_CREDENTIALS`, `INVALID_PASSWORD`, `EMAIL_NOT_FOUND` | `invalid_credentials` | «Неверная почта или пароль» (не различаем) |
| `TOO_MANY_ATTEMPTS_TRY_LATER`, HTTP 429 | `too_many_attempts` | «Слишком много попыток…» |
| `CREDENTIAL_TOO_OLD_LOGIN_AGAIN`, `TOKEN_EXPIRED`, `INVALID_ID_TOKEN` | `reauth_required` | «Нужен свежий вход…» |
| `USER_DISABLED` | `disabled` | «Этот аккаунт заблокирован» |
| `OPERATION_NOT_ALLOWED` | `not_available` | «Вход по почте сейчас недоступен» |
| нет сети / 5xx | `offline` / `server` | «Нет связи…» / «Сервер не отвечает…» |

Клиент проверяет до запроса: почта (одна `@`, точка в домене, ≤ 254), пароль 6–128 символов
(при входе — любой непустой); пароль не обрезается. Привязка, вход и сброс не повторяются
автоматически, двойное нажатие блокируется (`busy`).

## Ник и его уникальность без Cloud Functions

Документы:

| Путь | Содержимое | Кто пишет |
|---|---|---|
| `nicknames/{ключ}` | `{uid, nickname, createdAt}` | владелец, **только create** |
| `publicProfiles/{uid}` | `{nickname, nicknameNormalized, createdAt, nicknameChangedAt}` | владелец |

Ключ = нижний регистр, `ё→е`, пробел→`_` (`NicknameRules.normalize`). Первый выбор и смена —
**один атомарный `documents:commit`** (`Online._reserve`):

- первый ник: create `nicknames/{ключ}` + create `publicProfiles/{uid}` + set `nicknameTrace/{uid}`;
- смена: delete `nicknames/{старый}` + create `nicknames/{новый}` + update `publicProfiles/{uid}`
  + set `nicknameTrace/{uid}`.

Что гарантируют правила (`firestore.rules`, проверено тестами эмулятора):

- Занятый ключ создать нельзя: create поверх существующего документа — это update, а update
  запрещён. Два игрока, берущие имя одновременно, — выигрывает ровно один.
- `uid` в индексе = `request.auth.uid`; ник проходит политику (3–16 символов, латиница/
  кириллица/цифры (один алфавит на ник: латиница и кириллица не смешиваются, иначе «Аdmin» с кириллической А подделывал бы зарезервированное имя), одиночные пробел/`_` только между буквами, зарезервированные имена);
  ключ **проверяется** (нет заглавных `\p{Lu}`, совпадает с ником без учёта регистра —
  `lower()` в правилах знает только ASCII, поэтому RE2 `(?i)`).
- Один ник на игрока: индекс создаётся только если `publicProfiles/{uid}` в том же commit
  указывает на него (`getAfter`), а старый ключ в том же commit удалён (`existsAfter`).
  Нельзя накапливать имена и оставлять «осиротевшие» документы.
- Смена не чаще раза в 24 часа (`nicknameChangedAt == request.time`, сравнение с прежним).
  Часы 24 ч хранятся ещё и в `nicknameTrace/{uid}` (см. ниже), поэтому удаление профиля их
  не сбрасывает.
- Рекорд подписывается только своим зарезервированным ником или `Рыцарь`.

### Лимит 24 ч и удаление профиля (`nicknameTrace/{uid}`)

Раньше лимит обходился: удалить `publicProfiles/{uid}` + `nicknames/{ключ}` (это разрешено,
иначе нельзя удалить аккаунт) и создать ник заново как «первый, бесплатный». Теперь:

- `nicknameTrace/{uid}` = `{changedAt}` (серверное время). Каждый commit резервации/смены ника
  пишет его **без предусловия** (`set`: создаёт или заменяет), а правило профиля требует
  `getAfter(trace).changedAt == request.time` — профиль нельзя создать, не сдвинув часы.
- Правило следа: создать можно всегда (первый ник бесплатен); **переписать и удалить — только
  через 24 ч после `changedAt`**. Значит «удалил профиль → создал заново» упирается в след
  и в тот же лимит, а чужой uid не читает и не пишет его (только владелец).
- Удаление аккаунта остаётся возможным: клиент читает след и включает его удаление в commit,
  только если прошло 24 ч (иначе правило отклонило бы весь commit). Если сервер всё же
  ответил 403 (расхождение часов), commit повторяется без следа. Недавний след остаётся
  сиротой (uid + время, без ника; пользователь Auth удалён, так что документ мёртв). Его можно
  убрать TTL-политикой Firestore по полю времени или вручную; в `PRIVACY.md` это указано.
- Клиент до отправки проверяет те же 24 ч по профилю или, если профиля нет, по следу
  (`Online._nickname_clock_block`).

Клиент при отказе (403) читает `nicknames/{ключ}`: чужой `uid` → «имя занято», иначе
`denied`. Лимит 24 ч проверяется и на клиенте до отправки. Старые рекорды переименовываются
best-effort после смены. Оффлайн ник сохраняется на устройстве как «не подтверждённый» и
резервируется при ближайшей синхронизации; если его успели занять — флаг конфликта и новый
запрос ника.

Политика ника продублирована в `scripts/nickname_rules.gd` и `firestore.rules`. Согласие
проверяют `tests/nickname_cases.json` (Godot и эмулятор) и `tests/nickname_letters.json`
(каждая принимаемая буква получает в правилах тот же ключ; генерируется
`tools/gen_nickname_letters.gd`). Менять политику — только вместе, затем перегенерировать.

## Удаление аккаунта (клиентом)

«Профиль → Удалить аккаунт» (`Online.delete_account`):

1. один commit: удалить `nicknames/{ключ}` (если принадлежит вам), `publicProfiles/{uid}`,
   `nicknameTrace/{uid}` (если с последней смены ника прошло 24 ч), `runs/{uid}`,
   `users/{uid}`, `saves/{uid}` и рекорды `leaderboards/level_N/scores/{uid}` всех уровней;
2. Identity Toolkit `accounts:delete` с idToken (пользователь Auth);
3. стирание локальных данных и сессии, возврат к первому запуску.

Порядок «данные, потом пользователь»: после сбоя шага 2 повтор безопасен (удаление
отсутствующих документов проходит, `USER_NOT_FOUND` считается успехом). Если Auth требует
свежий вход (`CREDENTIAL_TOO_OLD_LOGIN_AGAIN`, возможно только для привязанного email), игрок
видит «данные в облаке удалены, нажмите «Войти заново» и повторите». Без сети удалить облачные данные
нельзя — интерфейс говорит об этом; локальные данные не трогаются до успеха. Без Firebase
стираются только локальные данные.

Чего удаление не делает: резервные копии Google хранятся по их политике (см. `PRIVACY.md`).

## Рекорды осады: проверка по времени (`runs/{uid}`)

Волны идут по фиксированным часам: волна N стартует через `first_delay + (N-1)*wave_duration`
= `N*30` игровых секунд после начала забега (`WavePlan`, `resources/levels.json`), раннего
вызова нет. Игра может идти на ×2, поэтому реально проходит не меньше `N*15` секунд.

- В начале бесконечной осады клиент пишет `runs/{uid} = {level: "level_N", startedAt}`
  (`Online.start_run`, серверное время `REQUEST_TIME`; правило требует
  `startedAt == request.time`, задним числом не поставить; новый забег перезаписывает документ).
- Рекорд `leaderboards/level_N/scores/{uid}` пишется `Online.submit_record` в commit с
  `updated = REQUEST_TIME` (раньше время слал телефон). Правило для новой или более высокой
  волны `w`: документ `runs/{uid}` существует, его `level` совпадает, и
  `request.time >= startedAt + (w-1)*15 с` (15 с запаса на запрос старта и сеть).
  Переименование записи после смены ника (волна и `updated` не меняются) проверки не требует.
- Верхние границы полей: `wave` — целое 1..4999, `name` ≤ 16 и только свой ник или `Рыцарь`,
  ключи ровно `name, wave, updated`.
- `tools/validate_project.py` проверяет, что у каждого уровня `first_delay` и `wave_duration`
  не меньше 30 — иначе границу в правилах пришлось бы ослабить. Меняя темп волн или
  максимальную скорость игры, меняйте и `minRunSeconds` в `firestore.rules`.

Что это даёт и чего нет — в разделе ограничений ниже.

## Честные ограничения (Spark, без серверной логики)

- **Лимит 24 ч** больше не обходится удалением профиля (`nicknameTrace`), но остаётся
  «вежливым»: новый анонимный аккаунт получает новый uid и новый бесплатный ник — аккаунты
  бесплатны (см. следующий пункт). Недавний след после удаления аккаунта остаётся мёртвой записью.
- **Захват имён несколькими анонимными аккаунтами**: каждый аккаунт держит один ник, но
  аккаунты бесплатны. Без серверной логики лечится только App Check (Play Integrity;
  требует нативного SDK — запрещён) и ручной модерацией (удалить документ в консоли).
- **Рекорды не доказывают честную игру.** Правила дают только **нижнюю границу времени**:
  волна 100 невозможна раньше ~25 минут после старта забега, «волну 4999 за секунду»
  отправить нельзя. Но кто готов подождать (запустить забег, простоять, отправить), или
  подделает клиент, всё равно получит любое значение, которое успевает «по часам».
  Не проверяются ни убийства, ни золото, ни построенные башни. Забег, начатый без сети,
  онлайн-рекорда не даёт (нет `runs/{uid}`); локальный рекорд при этом сохраняется. Несколько
  аккаунтов ждут параллельно. Настоящая проверка — реплей-журнал и перепрогон другими
  клиентами (`MULTIPLAYER.md`, §9), он требует детерминизма и пока не сделан.
- **Границы проверки времени**: 15 с запаса и ×2 заложены в правилах; клиент с изменённой
  скоростью (>×2) может «ускорить» волны сверх границы. Правила не знают реальной скорости.
- Одновременный забег на нескольких уровнях невозможен (один документ `runs/{uid}`), старт
  нового забега на другом уровне перезаписывает прежний: рекорд прошлого уровня после этого
  отправить уже нельзя (отправка идёт сразу после поражения, так что на практике не мешает).
- Модерации и жалоб в клиенте нет (коллекции отсутствуют, правила их запрещают).
- Правила и клиент не знают о состоянии «аккаунт заблокирован» кроме `USER_DISABLED` из Auth.

## Привязка к магазинам и публикация
